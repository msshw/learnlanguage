## Context

See proposal.md for motivation. Current state:

- `supabase/functions/autofill/index.ts`: session check, `{action: "usage"}` branch, `readTerm` (trim, collapse spaces, length and control-character checks), month spend through `ai_usage_since`, cap, model call with one retry, `validate()`, `logCall()`. It already holds a service-role client (`admin`).
- `src/js/lib/ai.js`: `suggest(term)` returns `{status, senses}` and maps every failure to `unavailable`; `invokeAutofill` lives in `db.js`.
- `src/js/pages/add.js`: picking a sense sets `source = 'ai_confirmed'`; editing afterwards keeps it. `word-form.js` has `buildWord(raw)` (cleanup and validation) and `senseToFormValues(sense)`.
- Every existing table has `user_id` and owner-only RLS; deletes are revoked for clients.

## Goals / Non-Goals

**Goals:**
- No client path can put text into the shared store: content only ever comes from validated model output inside the function.
- The client change is one extra fire-and-forget call after a save.

**Non-Goals:**
- Caching `not_a_word` results or failures.
- Expiring or cleaning up old candidates (see Risks).
- Moderation, reports and soft delete of records (`suggestion-admin`).
- Invalidating the store when the prompt or model changes (manual SQL by `model` for now).

## Decisions

**Table `ai_suggestions`.** Columns: `id uuid pk default gen_random_uuid()`, `target_lang`, `native_lang`, `term_key text`, `corrected_key text`, `senses jsonb` (the validated array), `model text`, `status text check in ('candidate','confirmed')`, `created_at`, `confirmed_at`. Indexes on `(target_lang, native_lang, term_key)` and `(target_lang, native_lang, corrected_key)`, both `where status = 'confirmed'`. RLS enabled, no policies, `revoke all ... from anon, authenticated`. The service role bypasses RLS. No unique constraint on keys: two users missing at the same moment may both confirm; the lookup takes the newest `confirmed_at`. Alternative: a partial unique index with conflict handling on confirm; more code for a race that only costs a duplicate row. Rejected.

**Keys.** A pure `cacheKey(term)` in a new `supabase/functions/autofill/cache.ts`: trim, collapse whitespace, `toLowerCase()`. The function computes both keys; the database only compares. `corrected_key` comes from `senses[0].term`.

**Lookup.** Two `.eq()` queries (entered key, then corrected key), each `status = 'confirmed'`, ordered by `confirmed_at desc`, `limit 1`. Alternative: one `.or()` filter; it would splice user text into a PostgREST filter string. Rejected. Lookup errors are logged and treated as a miss.

**Order in the function.** session → body → `usage` / `confirm` branches → `readTerm` → lookup → (hit: reply) → spend and cap → model → on `ok`, insert candidate → reply. The hit is before the cap so cached answers stay free and available over the cap, as Maks decided.

**Response.** `reply()` grows to `{status, senses, suggestion_id, confirmed}`. The spec uses `suggestion_id` for both hit and miss (on a miss it is the candidate id) because `suggestion-admin` needs an id to report either kind.

**Confirm.** `{action: "confirm", suggestion_id, sense_index}`: check the id is a UUID and the index an integer, select the row, check `0 <= index < senses.length`, then `update ... set status='confirmed', confirmed_at=now() where id=$1 and status='candidate'`. Only those two fields are read from the body. `sense_index` is checked but not stored: the whole record is promoted, and storing the index would add a column nobody reads. Any signed-in user holding the id may confirm; ids are random UUIDs that only reach the user whose request created the candidate, and the content was generated by the model in any case.

**Client.** `ai.js`: `suggest()` passes through `suggestionId` and `confirmed`; new `confirmSuggestion(id, senseIndex)` with the same timeout wrapper, never throws. `word-form.js`: pure `matchesSense(value, sense)` compares the `buildWord` value with `buildWord` of `senseToFormValues(sense)` on term, part of speech, translations, hint, forms and examples (notes and tags ignored). `add.js` keeps `picked = {suggestionId, confirmed, index, sense}` and after a successful `insertWord` calls `confirmSuggestion` without awaiting when `!confirmed && suggestionId && matchesSense(...)`. `source` rules are unchanged.

**Tests.**
- Unit: `cacheKey` (spaces, case, umlauts); `matchesSense` (unchanged, each field changed, notes and tags added, noun forms order); `suggest` passing the new fields; `confirmSuggestion` (ok, failure, timeout).
- Integration (`tests/integration`, local Supabase): alice and anon cannot select, insert, update or delete `ai_suggestions`; service role can insert.
- E2E (`autofill.spec.js`, stubbed function): an unchanged pick sends exactly one confirm with the stubbed id and the picked index; an edited pick and a `confirmed: true` response send none; a failing confirm still shows "Word saved".
- Manual (Maks, `supabase functions serve autofill`): request `Bank` twice as alice with an unchanged save in between; the second response has `confirmed: true` and `ai_calls` has no new row.

## Risks / Trade-offs

- [A wrong but unchanged suggestion gets confirmed and reaches every user] → removal by SQL now; `suggestion-admin` adds reports and soft delete.
- [Unconfirmed candidates pile up] → small rows; `ponytail:` note in the migration: delete candidates older than 30 days by SQL or cron if the table grows.
- [Prompt or model change leaves old answers in the store] → `model` column lets the owner delete by model with SQL.
- [Timing reveals that someone looked a word up before] → only common German words, no user data; accepted.
- [Exception to the per-user data rule] → recorded in the data-access-control spec; docs below.

## Migration Plan

New migration `<timestamp>_ai_suggestions.sql` (table, indexes, RLS, revokes). Order when deploying: migration, function, site. The old client ignores the new response fields, so the function can ship first. Rollback: redeploy the previous function; the table can stay.
