## Context

See proposal.md. Builds on `ai-word-cache` (archived: `ai_suggestions`, lookup/confirm in `autofill`) and `sidebar-polish`. `profiles` has an owner update policy that would let a user change any column, including `is_admin`. `sidebar.js` already reads the profile for the due count. Edge functions are called from `db.js` with `supabase.functions.invoke`.

**State of the code (revision 2).** The first version of this change is already implemented and not archived: migration `20261013100000_suggestion_admin.sql` (applied; never edited), the `admin` function (`list`, `remove`, `keep`, `group.ts`), `autofill` with `deleted_at` filters, plus page, nav and tests. Today moderation is record-level: `ai_suggestions.status` (`candidate`/`confirmed`) and `deleted_at`; `suggestion_reports(user_id, suggestion_id, created_at, closed_at, resolution in (removed, kept))` with no reason; `moderate_suggestion(p_id, p_remove)`; `confirm` flips the whole record. This revision is the delta from there, in a second migration.

## Goals / Non-Goals

**Goals:**
- The admin check happens on the server for every admin request; the client flag only hides the link.
- Judge each sense separately: unverified senses are still shown, verified ones are marked, bad ones never come back.
- A report stays open until the admin has judged every sense (or removed the record).
- Every sense write (confirm, approve, edit, reject) is atomic and idempotent.

**Non-Goals:**
- Reporter picks a sense, report history for users, notifications.
- More than one admin or an admin management UI (`is_admin` is set by SQL).
- Semantic matching of rejected senses.
- A sub-navigation for the admin area (users list, other table views): a LATER change. The tabs added here are only sections by status on the one admin page, built from a small section list so more can be added.
- Undoing "Allow again" from the page (the sense can be rejected again from a report).
- Showing users a verified/unverified badge (state is in the response; UI does not use it beyond deciding on confirm).

## Decisions

**Sense state.** Each element of `ai_suggestions.senses` gets a `state` key (`candidate` | `confirmed` | `rejected`). The record keeps `status` (`confirmed` iff at least one sense is confirmed, else `candidate`) and `confirmed_at` (latest confirmation) as a maintained summary, so the existing partial indexes and the lookup filter keep working. They are written only by the SQL functions below. `deleted_at` stays in the table but nothing writes it any more; the lookup keeps its `deleted_at is null` filter (harmless). Alternative: drop `status`/`confirmed_at` and query `senses @> '[{"state":"confirmed"}]'`; rejected, it loses the partial indexes for no gain. Sense content is stored as before; `state` is stored beside it, and so is `judged` (boolean, absent = false). `judged` is what separates "confirmed by a user's unchanged save" from "approved by an admin": it is set only by `moderate_suggestion` (approve, edit), never by `confirm_sense`. A sense is judged iff `state = 'rejected'` or `judged = true`. `validate()` strips unknown keys, so `state` and `judged` are added after validation and never accepted from input.

**Migration 2** (new file, e.g. `20261014100000_suggestion_senses.sql`; the applied one stays untouched):
- Data: for every `ai_suggestions` row set each sense's `state`: `deleted_at is not null` gives all `rejected` and `status = 'candidate'`; `status = 'confirmed'` gives all `confirmed`; otherwise `candidate`. Accepted simplification: the old record-level confirm happened when ONE sense was picked and that index was never stored, so all senses of a previously confirmed record become confirmed. The admin can reject any wrong one. No sense gets `judged` in the conversion, except rejected ones (judged by state). Fingerprints of the removed records are NOT written in SQL; see **Backfill** below.
- `suggestion_reports`: add `reason text`, check `char_length(btrim(reason)) between 50 and 2000` (nullable, so existing rows stay valid); replace the insert policy so the check also requires `reason is not null`; widen the `resolution` check to `removed, kept, approved, edited, rejected` (`kept` is legacy). Unique pair unchanged, so a repeat report succeeds client-side via the existing `23505` mapping and keeps the first reason.
- `rejected_senses(id, target_lang, native_lang, term_key, fingerprint, part_of_speech, translations text[], created_at)`, unique `(target_lang, native_lang, term_key, fingerprint)`, RLS on, `revoke all` from `anon, authenticated`, no policies, no `user_id`.
- Implementation note: `moderate_suggestion` has a sixth defaulted parameter `p_corrected_key` for the edit-at-index-0 case (the key is computed in code and passed in, as written below), so the five-argument call in the task list still works for the other actions.
- Functions, `security invoker`, `search_path = ''`, execute granted to `service_role` only:
  - `confirm_sense(p_id, p_index)`: row lock, if the sense is `candidate` set it `confirmed`; if `confirmed` do nothing; if `rejected` or out of range or unknown id, raise (the function maps to `{status: "error"}`). Recomputes `status`, `confirmed_at`.
  - `moderate_suggestion(p_id, p_action, p_index, p_sense, p_fingerprints)` replaces the old two-argument function (dropped in this migration; the admin function is its only caller). Actions: `approve` (sense to confirmed), `edit` (sense replaced by `p_sense` plus `state: confirmed`; if index 0, `corrected_key` follows the new term, the key computed in code and passed in), `reject` (sense to rejected, and insert its fingerprint under `term_key` and `corrected_key` with `on conflict do nothing`), `remove` (every non-rejected sense rejected, same inserts). All under one row lock; set `judged = true` on the approved or edited sense; recompute `status`; then run the closing check: if no non-rejected sense has `judged` false (or the action was `remove`), close the suggestion's open reports with resolution = this action (`approved | edited | rejected | removed`), else leave them open. The check runs after every action, also an approve of an already judged sense, so a late report on a fully judged record can be closed by one approve. The function returns the updated senses (state, judged) and `reports_closed` (boolean) for the in-place re-render. Anything wrong raises, so nothing is half done.
  - Fingerprints are computed in code (`fingerprint.ts`, pure) and passed in, so the rule lives in one place and is unit-tested.

**Reopen rule for first-version reports.** The first version closed every report on its first admin action. Migration 2 reopens (sets `closed_at` and `resolution` to null) every closed report whose suggestion still has a non-rejected sense that is not judged, evaluated after the state conversion. Legacy `kept` closed reports without judging any sense, so those reopen. Legacy `removed` belongs to records with `deleted_at`, whose senses are now all rejected (judged), so those stay closed. The same test is the closing rule, so a closed report on a fully judged record is also left alone. The rule lives in the service-only function `reopen_unjudged_reports()`, which the migration calls once; a function (not an inline statement) so the integration test can run the same SQL on seeded legacy-shaped data. It is idempotent.

**Backfill of first-version removals.** Records with `deleted_at` not null end migration 2 with all senses `rejected`. Their fingerprints must equal what `fingerprint.ts` computes, or the filter would miss them. Options: (a) compute in SQL: rejected, because JS `toLowerCase`/`trim`/default sort differ from Postgres `lower`/`btrim`/collation on non-ASCII text (German umlauts, ß), so the two could drift silently and the migration is hard to change once applied; (b) a one-off script. Chosen: (b) `scripts/backfill-rejected-senses.ts`, run by Maks with the service role after migration 2 and before the functions are deployed. It reads records where `deleted_at is not null`, builds rows through a pure exported `backfillRows(records)` that imports `fingerprint.ts` (one rule, one place), and upserts into `rejected_senses` under both keys with `on conflict do nothing`, so reruns are safe. Runtime: Node (decided; it is already installed, and Node 22.18+ runs the `.ts` file and imports `fingerprint.ts` directly), started with `npm run backfill:rejected`. Covered by a unit test of `backfillRows` and a service-role integration test (seed a deleted record with umlaut translations, run, compare with `fingerprint.ts`, run twice, count unchanged). The migration cannot do this itself, so the order below matters: until the script runs those meanings are not filtered.

**Fingerprint.** `part_of_speech + '|' + sorted(lowercase(trim(translation))).join(',')`. Known limit: matching is exact. The model may rephrase a rejected sense ("financial institution" vs "bank (money)"); the prompt avoid list reduces that, and the admin can reject again.

**autofill changes.**
- Lookup: select records matching `term_key`/`corrected_key` with `status = 'confirmed'` and `deleted_at is null`, newest `confirmed_at` first; take the first with at least one non-rejected sense (always true if it has a confirmed sense). Return the non-rejected senses as `{...sense, index, state}`, `confirmed: true`.
- Miss: read `rejected_senses` for `term_key` (the request key; rows exist under both keys of a record). Add them to the user message (a "Do not suggest these senses" block, one line per sense, only when there are any; both attempts). Filter validated senses by fingerprint. Nothing left on attempt 1: this is treated like a validation failure and uses the existing second attempt. Attempt 2 builds the user message with a stronger avoid block (the same senses, an explicit "these exact meanings must not appear" line before and after the request). Never more than two model calls per request, validation failures and all-rejected results share them. Nothing left after attempt 2: `reply('error')`, the status the client already maps to the manual form with "Suggestions unavailable" (no new status, no new message); nothing is stored. Each attempt that was all dropped is logged to `ai_calls` with `ok` false, real tokens and error "all senses rejected"; since failed calls with tokens already count toward the cap, both count (the spend is real). Some left: insert the record with every sense `candidate`, `corrected_key` from the first remaining sense. Failure to read the rejected list is logged and the call proceeds without it.
- Confirm: `confirm_sense` RPC instead of the record update; the picked stored `index` matters. The edge function still reads only id and index.
- `index` and `state` are added to each returned sense; for a fresh miss `index` is the position and `state` `candidate`. `confirmed` in the response now means "came from the cache".

**Prompt size.** The avoid block adds a few tokens and only for terms with rejections. It is in the user message, not the cached system prompt, so the prompt cache is unaffected. Cap the list at 10 senses.

**admin function changes.** Actions: `list` (also returns `reason` per report and per-sense `state`; `group.ts` collects reasons), `approve`, `edit`, `reject` (each `{suggestion_id, sense_index, ...}`), `remove`. `keep` is removed. `edit` takes `sense` (term, part_of_speech, translations, hint_en, forms, example_de, example_en) and runs `validate({is_german_word: true, senses: [sense]})`; invalid gives `{status: "invalid", error}` and no write. Reused code: `admin` imports `validate.ts` and the new `fingerprint.ts` from `../autofill/`. Risk: deploy bundling of a cross-function import; fallback is to move both (and the constants `validate.ts` needs from `config.ts`) to `supabase/functions/_shared/`. Decide when implementing; verify with `supabase functions serve` and a deploy dry run by Maks.

**Reporting.** `reportSuggestion(id, reason)` in `db.js` inserts `{user_id, suggestion_id, reason}` (no `select()`), trims the reason, rejects client-side outside 50 to 2000, and still treats `23505` as success. `add.js`: "Report suggestion" reveals a `<textarea>` with a count and "Send report" (disabled below 50); the existing key handling already ignores keys typed in inputs, to be confirmed in the code. No sense picker.

**Admin page.** Entry per suggestion: header (term, pair, report count, first report time), reasons in a list (`textContent`), senses with a state label and, for non-rejected senses, "Approve as is", "Edit and approve", "Reject"; entry-level "Remove suggestion". "Edit and approve" swaps the sense for a form built from the Add word form pieces (extract the field builders from `add.js` into `word-form-view.js`, no notes/tags), "Save sense" and "Cancel". Each sense shows its state and "Judged" or "Not judged". After any action the page re-renders that entry from the response in place (states, judged labels, "Reports closed" when `reports_closed`); a closed entry is gone on the next load, an open one stays listed with its remaining unjudged senses.

**Allow again (revision 3).** Adds a status section to the Admin page and a way to restore a rejected sense.
- *Sections.* `admin.html` gets a tablist ("Open reports", "Rejected") with `role="tab"`, `aria-selected`, `aria-controls`, roving `tabindex`, and Left/Right/Home/End keys that select the tab. Each tab has a `role="tabpanel"`. `admin.js` keeps a small `SECTIONS` table `{id, load}` so another section is one more tab, panel and loader. A section loads on first selection and again when marked stale (allowing a sense again marks "Open reports" stale, since sense states change). The non-admin "Not available" state hides the tabs.
- *Source of the list.* The `rejected_senses` table, not `ai_suggestions`: the forever list exists after the suggestion is gone. `list_rejected` reads at most 500 rows, newest first (`ponytail:` comment: cap, page it if the store ever passes that; a group cut at the cap shows with fewer keys).
- *Grouping.* One rejection writes the same sense under up to two keys (`term_key` and `corrected_key`) in one statement, so those rows share `created_at`. An entry is (target_lang, native_lang, fingerprint, created_at); its `ids` are the row ids, its `keys` the term keys (shown joined by " / " as the term). Grouping by pair and fingerprint alone was rejected: two different words can share a fingerprint (same part of speech and translations) and allowing one must not unblock the other. Known limit: a key written by a later rejection of the same sense (the unique key keeps the older row) shows as its own entry. The grouping is pure (`groupRejected` in `group.ts`) and unit-tested.
- *Admin actions.* `list_rejected` (no input) returns `{status: "ok", entries: [{ids, term, keys, target_lang, native_lang, part_of_speech, translations, rejected_at}]}`. `allow_again` takes `{ids: [..]}` only: 1 to 20 distinct positive integers, else `{status: "error"}`. The function reads those rows with the service role (all must exist and share pair and fingerprint), finds the suggestions of that pair whose `term_key` or `corrected_key` is among the entry's keys, computes the fingerprints of their senses in code (`fingerprint.ts`, one rule in one place) and calls the database function. Nothing about the caller or suggestion content comes from the client; the admin check is the same per-request `is_admin` read.
- *Database function* (new migration `20261015100000_allow_sense_again.sql`, never editing the earlier ones): `allow_sense_again(p_ids bigint[], p_records jsonb)`; `security invoker`, `set search_path = ''`, execute revoked from `public, anon, authenticated`, granted to `service_role`. In one transaction: lock and read the rows for `p_ids` (raise if any id is missing or the rows do not share pair and fingerprint); delete them; for each `{id, fingerprints}` in `p_records` lock the suggestion, check it is of the same pair and one of its keys is among the deleted rows' keys and the fingerprint array matches its sense count (else raise), set every sense that is `rejected` with the entry's fingerprint to `candidate` and drop its `judged` key, and recompute `status` (`confirmed` if any sense is confirmed, else `candidate`). `confirmed_at` and `deleted_at` are left alone; reports are not touched. Returns the number of store rows deleted. Anything wrong raises, so nothing is half done. The sibling key of a rejection is deleted too only if its row id is in `p_ids` (the list gives the whole entry's ids).
- *First-version deleted records.* `deleted_at` stays set. The allowed sense becomes a candidate and status is recomputed (candidate, since all other senses stay rejected). The lookup requires `status = 'confirmed'` and `deleted_at is null`, so the record is still not served; the next request is a miss, the model may suggest the sense and a fresh candidate record is stored.
- *Suggestion already gone.* No record matches; the rows are deleted and nothing else changes.
- *Page.* Each entry shows term, pair, part of speech, translations, "rejected <time>" and one "Allow again" button (disabled while the request runs); on success the entry is removed from the list; on failure "Could not allow the sense again" and nothing changes. Load error "Could not load the rejected senses." with "Retry"; empty "No rejected senses".

**Nav entry.** As before: `{id: 'admin', href: '/admin.html', label: 'Admin', adminOnly: true, code: 'KeyM', chip: 'Alt+M', icon}`, rendered hidden, revealed from the single profile read; `shortcutTarget` skips hidden links.

## Risks / Trade-offs

- [A user floods reports] → one report per user per suggestion, reason of at least 50 characters; single-owner app for now.
- [Old confirmed records have all senses confirmed] → accepted simplification; admin rejects wrong ones.
- [Rejected sense comes back rephrased] → known limit of fingerprint matching; avoid list in the prompt helps; admin rejects again.
- [Filter leaves nothing twice, user sees "Suggestions unavailable"] → they add the word by hand; both model calls are paid, logged and counted toward the cap. Worst case adds one extra call per such lookup.
- [Backfill script not run] → removed meanings can return until it runs; the order in the migration plan prevents it, and rerunning is safe.
- [Entry stays listed if the admin leaves a user-confirmed sense unjudged] → intended; "Approve as is" on it is one click.
- [Unverified senses are served from a record with one confirmed sense] → intended, so every meaning shows; a wrong unverified sense can be reported, and the first unchanged save of it confirms it (one user's save is the only check, as before).
- [`is_admin` set by mistake via the service role] → only the owner's SQL and the admin function hold that key; the function never writes `profiles`.
- [Two entries for one sense after a later re-rejection under a new key] -> allow each; harmless, the lookup reads by key.
- [Allow again on a sense the model keeps getting wrong] -> it returns as an unverified candidate and can be reported and rejected again.
- [Cross-function import bundling] → see admin function changes.

## Migration Plan

Apply after `ai-word-cache` and the first `suggestion_admin` migration. Order: migration 2 (data conversion runs inside it; the allow-again migration `20261015100000_allow_sense_again.sql` follows it and can be applied with it), then the backfill script, then `autofill` and `admin` functions together (the old functions read `status` and `deleted_at` and would still run against the new data, but the old `moderate_suggestion` is dropped, so deploy `admin` right after), then the site. The owner flag is set by hand: `update profiles set is_admin = true where id = '<owner uuid>';`. Rollback: redeploy the previous functions and restore the dropped function; sense `state` keys and new columns are ignored by the old code.
